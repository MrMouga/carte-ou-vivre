# Matrice d'openrouteservice : aucun rayon d'accroche à régler, et écarter les bacs la fait tomber à 25 trajets par requête
Étiquettes : data, outil · Tranche : recherche-et-mer · Source : tâche 0a de /build recherche-et-mer, `docs/plans/2026-11-25-recherche-et-mer/mesure-tache-0.md`

**Problème** — Le plan demandait de fixer le rayon d'accroche des points de côte (H196) et d'écrire si la matrice peut écarter les bacs, d'après la documentation.
**Symptômes** — Les pages de l'API (« matrix », « restrictions ») ne disent rien du rayon ni des bacs. La page des restrictions de l'API hébergée a deux lignes : 3 500 trajets (« origin x destination ») par requête, et 25 « with dynamic arguments ».
**Ce qui n'a pas marché** — Chercher un paramètre `radiuses` (il n'existe que pour l'itinéraire, pas pour la matrice) ; la page de référence de la matrice renvoie au « playground ».
**Ce qui a marché** — Lire le code d'openrouteservice sur GitHub : `MatrixRequest.java` (paramètres : locations, sources, destinations, metrics, resolve_locations, units, et deux cachés, `optimized` et `options`) ; `isFlexibleMode` : `options.avoid_features` (donc éviter les bacs) passe la matrice en mode « flexible », celui des 25 trajets. Le rayon est un réglage du serveur, `maximum_search_radius`, 2 000 m par défaut (documentation de configuration) ; un point non accroché revient sans `location` et ses durées à `null` (`MatrixSearchContextBuilder`), sans faire échouer la requête. Les bacs restent ; la réponse entière est gardée pour mesurer l'accroche réelle (`snapped_distance`).
**Prévention** — Règle de jugement : pour une limite ou un réglage d'une API ouverte que la documentation tait, lire le code source de la requête avant d'écrire une hypothèse ; garder la réponse entière d'un calcul unique, pour compter les causes sans relancer.
