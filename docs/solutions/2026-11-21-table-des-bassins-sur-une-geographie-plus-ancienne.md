# Une table « 2026 » d'un producteur n'est pas forcément sur le COG 2026 : regarder dans quel sens recaler avant d'écrire la règle
Étiquettes : data, discovery · Tranche : emploi · Source : tâche 0a de /build emploi, `docs/plans/2026-11-21-emploi/taches/T0a.md`

**Problème** — Relier les 34 746 communes de la carte (COG 2025) aux bassins d'emploi par la « table des bassins d'emploi 2026 » de France Travail ; 12 codes absents (H142). Le plan supposait des fusions de 2026 : « la commune 2026 qui les a reprises ».
**Symptômes** — Aucune des 12 n'a de mouvement en 2026. Onze sont des changements de code de 2024-2025 (Conques-en-Rouergue 12076 → 12218, Orée d'Anjou 49069 → 49126…) ou des communes rétablies (Celles, Chalinargues… sorties de Neussargues 15141 le 1er janvier 2025) : la table porte encore l'**ancien** code. La douzième, Yvrench (80832), n'a aucun mouvement : elle manque simplement à la table. Autre surprise du même fichier : 435 lignes BMO « en double » (métier, bassin, comité local) sont en fait une ligne par département, aux chiffres différents (12 couples à cheval sur deux départements) : des parts à additionner, pas des copies (l'inverse de la DVF).
**Ce qui n'a pas marché** — Suivre les mouvements vers l'avant (ancien code → nouveau) depuis la commune de la carte.
**Ce qui a marché** — Remonter les mouvements (nouveau code → ancien code ou commune d'origine, MOD 50 et 21) jusqu'à un code de la table ; contrôle « les 12 attendues, et elles seules » qui a montré Yvrench. Pour les doublons : clé avec le département, comparer les valeurs avant de décider « parts » ou « copies ».
**Prévention** — Règle de jugement : avant d'écrire une règle de recalage, ouvrir les mouvements des codes absents dans les deux sens et noter le millésime réel de la table (pas celui de son nom). Contrôles dans `scripts/data/emploi.py` (liste exacte des recalées, une ligne par métier × bassin × comité local × département).
